Le référentiel conserve les mappings des codes locaux AP-HM vers les concepts standards OMOP (table source_to_concept_map), version par version. Chaque version publiée correspond à un CDM généré.

Le cycle d'une version

  1. Créer la staging (Releases) : copie complète de la dernière version publiée.
  2. Importer des fichiers CSV / Excel (Import) ou corriger un code depuis sa fiche (Recherche › clic sur un code › Modifier).
  3. Vérifier les changements (Comparer).
  4. Promouvoir la staging en nouvelle version majeure, puis la publier avec la référence du build CDM.
  5. Exporter la version publiée (Export) : fichiers properties, CSV CDM ou CSV complet.

Statuts d'un mapping

Dans une version publiée, tout est validé. Dans la staging, tout ce qu'un import ajoute ou modifie est UNCHECKED (à relire) ; on peut le passer FLAGGED ou IGNORED depuis la fiche. À la publication, les UNCHECKED deviennent APPROVED ; s'il reste des FLAGGED, la publication est refusée. Un import peut être annulé tant que la staging est ouverte ; après publication, il est archivé.

APPROVEDValidé par un relecteur.
UNCHECKEDProposé, pas encore relu.
FLAGGEDSignalé : à revoir.
IGNOREDÉcarté : exclu des exports CDM et properties.

Bon à savoir

  • Saisissez votre nom en haut à droite : il est enregistré dans l'historique de vos imports et corrections.
  • Une version publiée ou archivée n'est plus modifiable ; la fiche d'un code propose alors de le corriger dans la staging.
  • Les actions irréversibles (publier, promouvoir, remplacer un vocabulaire) demandent toujours une confirmation.
